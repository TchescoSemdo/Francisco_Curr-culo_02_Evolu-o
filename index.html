ℹ️ O que é ABT (Account-Based Ticketing)?

ABT é a evolução da bilhetagem eletrônica tradicional. Em vez de "valor no cartão" (card-centric), o saldo fica na conta do usuário na nuvem. O cartão/QR Code é apenas um identificador. Vantagens: recarga remota instantânea, múltiplos dispositivos (cartão + app), histórico completo, bloqueio/desbloqueio remoto, e integração com pagamentos digitais (PIX, cartão).

Quality-Driven Development (QDD)

O que é QDD?

Quality-Driven Development é a evolução do Shift-Left Testing. Enquanto Shift-Left antecipa a execução de testes, QDD antecipa as decisões de qualidade.

Não se trata apenas de "testar mais cedo", mas de definir qualidade antes do código existir: requisitos não-funcionais, critérios de aceite técnicos, estratégias de rollout, métricas de observabilidade e análise de risco.

Aplicação Prática

Discovery & Refinamento
  • QA participa como consultor técnico
  • Perguntas críticas: impacto financeiro, idempotência, timeout, concorrência, estados inválidos
  • Geração do Quality Requirements Document (QRD)
  • Transformação de riscos em acceptance criteria
Development
  • Daily QA Sync (10min): dev atualiza, QA questiona, alignment
  • Bugs encontrados em horas, não dias
  • Modelo embedded: QA integrado no squad
  • Revisão contínua de código com foco em testabilidade
Testing
  • Pirâmide de testes orientada a risco
  • Features de alto risco: mais integration/chaos tests
  • Automação focada em cenários críticos
  • Validação de quality gates no CI/CD
Production
  • Observabilidade como extensão de qualidade
  • Métricas Prometheus, dashboards Grafana
  • Alertas direcionam troubleshooting
  • RCA feed back para Discovery (aprendizado sistêmico)

Pipeline de Identidade Dinâmica: Automação E2E

Status: 🚧 Em Construção | Fase Atual: Integração de APIs | Próxima Fase: Automação de Front-end

Objetivo Estratégico

Resolver o maior gargalo dos testes de QA: a dependência de massa de dados pré-existente. Muitas vezes, testes falham porque um usuário já foi usado ou o CPF já está cadastrado. Nossa solução cria um usuário "virgem", valida-o através de APIs de terceiros e entrega uma sessão autenticada em segundos.

Arquitetura do Pipeline

ETAPA 1: API de Registro

Endpoint: /auth/register

O processo nasce aqui. O objetivo é registrar um usuário funcional no banco de dados.

Motor de Dados (Pre-request Script):
  • Identidade Única (Contador): Script lê contador global, soma +1 e salva. Garante que e-mail e nome nunca se repitam
  • Validação de CPF Real: Executa lógica matemática de verificação que calcula os dígitos finais. Não é gerador aleatório, é fórmula que garante que o backend reconheça o documento como legítimo
sequentialName: "Teste QA " + Contador → "Teste QA 02" email: "testeqa" + Contador + "@mailsac.com" → "[email protected]" cpf: Matemática de Validação Real → "123.456.789-01" password: Padrão de Teste → "123456789"
ETAPA 2: Triangulação de E-mail (Mailsac API)

Após o registro, o usuário está no banco mas bloqueado. Precisamos do código de 6 dígitos enviado por e-mail para desbloqueio.

Passo 1: Localizando a Mensagem

GET /addresses/{email}/messages

  • Automação faz GET na API do Mailsac
  • Script lê lista de mensagens e pega o ID da primeira (mais nova)
  • Salva ID na variável {{last_message_id}}
Passo 2: Capturando o Código (Regex)

GET /messages/{message_id}

  • Segundo GET para ler conteúdo interno do e-mail
  • Filtro Inteligente (Regex): /\d{6}/ ignora palavras e foca apenas em sequência de 6 números
  • Código capturado e salvo em {{validation_code}}
ETAPA 3: UPDATE CODE API

Endpoint: /auth/update-code?email={email}&code={code}

Automação possui ID do usuário (do Registro) e código (do E-mail). Chama API de Update enviando esses dados.

O que acontece: Servidor valida código e altera status do usuário para "False" no campo au_is_blocked na tabela tmobapp.app_users. Sem isso, usuário existe mas não consegue logar.

ETAPA 4: Login API

Endpoint: /auth/login

O ciclo termina com POST Login usando e-mail e senha gerados no início.

  • Sucesso: Servidor retorna Token JWT
  • Importância: Este token é a prova de que todo o fluxo funcionou. Agora, qualquer outra API de teste pode usar esse {{auth_token}} para realizar compras, editar perfis, etc.

Jornada de Escolha da Ferramenta (R&D)

Não chegamos ao Mailsac por acaso. Testamos principais soluções do mercado:

  • Mail7 & Guerrilla Mail: Descartados por instabilidade nos domínios e bloqueios frequentes
  • Mailtrap: Excelente interface, mas limitações de custo/benefício para volume de testes
  • Mailslurp: Robusto, porém configuração excessivamente complexa
  • Mailsac (Escolhida): API REST direta, consulta caixas de entrada dinâmicas sem criar conta no painel. Encadeamento direto e veloz - ciclo completo em segundos
