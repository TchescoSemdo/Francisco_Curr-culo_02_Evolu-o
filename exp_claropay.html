CloudWatch + DynamoDB - Troubleshooting e Análise de Causa Raiz
  • AWS CloudWatch para investigação profunda:
    • Validação em tempo real: Monitoramento de métricas críticas (latência, taxa de erro, throughput)
    • Análise de causa raiz: Correlação de logs entre Lambda, API Gateway, DynamoDB para identificar origem de falhas
    • Identificação de padrões anômalos: Detectar anomalias (ex: 50 transações falhando com mesmo cartão em 5 minutos → provável fraude ou bug)
    • Acompanhamento e citação: Compartilhar logs específicos com Devs e PO em comentários de tickets Jira (link direto para CloudWatch com timestamp e filtros aplicados)
  • DynamoDB - Análise de dados transacionais (NoSQL):
    • Validação de persistência de dados:
      • Busca por transactionId (partition key) para verificar se transação foi persistida
      • Validação de atributos: transactionStatus, value, tokenCard, updatedDate, createdDate
      • Verificar timestamps para detectar delays anormais (ex: transação criada às 14:30 mas só atualizada às 14:45 = 15min de delay)
    • Estados de transação analisados:
      • INICIO_PAGAMENTO → Transação iniciada pelo usuário
      • EM_CAPTURA → Enviado para processadora (Cielo)
      • CAPTURADA_FINALIZADA → Captura bem-sucedida ✅
      • AUTORIZADA → Pré-autorização (crédito reservado mas não capturado)
      • ESTORNO → Transação revertida (cancelamento ou chargeback)
      • ERRO_GATEWAY → Falha na comunicação com processadora
    • Análise de antifraude (MDD):
      • Atributo antifraud.decision: "ACCEPT" (aprovado), "REJECT" (rejeitado), "REVIEW" (revisão manual)
      • Atributo antifraud.reasonCode: "100" (transação limpa), "200" (risco médio), "400" (alto risco)
      • Validação de consistência: Se responseDescription = "APPROVED" mas decision = "REJECT" → Bug no fluxo de antifraude que precisa ser reportado
    • Rastreamento de wallet (cartões vinculados):
      • Busca por identificador do cliente (CPF/UUID) para listar cartões vinculados
      • Validar estrutura de dados: token, flag (MASTERCARD, VISA), cardNumber (últimos 4 dígitos), cardExpirationDate
      • Verificar status de cartão: isDeleted: false (ativo) vs isDeleted: true (removido pelo usuário)
    • Operações NoSQL utilizadas:
      • GetItem: Busca por chave primária (transactionId) - operação mais rápida (< 10ms)
      • Query: Busca por partition key + range de sort key (ex: todas transações de um usuário em determinado período)
      • Scan (evitado): Varredura completa da tabela - usado apenas em análises offline (alto custo de leitura)
    • Exemplos de investigação:
      • Buscar transação específica → Analisar campo retryCount: se > 0, indica que houve tentativas de reprocessamento (instabilidade)
      • Filtrar transações por valor (ex: R$ 150,00) → Validar se cálculo de impostos/taxas está correto
      • Analisar distribuição de transactionStatus → Quantas CAPTURADA vs ESTORNO vs ERRO para identificar taxa de falhas
  • War Room - Trabalho conjunto com DevOps:
    • Salas de guerra para incidentes críticos em produção:
      • Reunião emergencial (Google Meet/Zoom) com QA, Devs, DevOps, PO, Suporte N3
      • Objetivo: Resolver incidente P1 (sistema fora do ar, transações falhando em massa) em < 2h
    • Metodologia de investigação colaborativa:
      1. 1. Identificação: QA reporta sintoma (ex: "100% das transações com cartão Mastercard falhando desde 14:30")
      2. 2. Investigação paralela:
        • QA: Testa cenários (só Mastercard? Só valores > R$ 100? Só app Android?)
        • DevOps: Checa saúde de serviços (Lambda com timeout? DynamoDB com throttling? API Gateway com 502?)
        • Dev: Analisa logs de aplicação (exception stack trace, última alteração deployada)
      3. 3. Hipóteses: Levantamento de possíveis causas (deploy recente? Mudança em configuração? Problema na Cielo?)
      4. 4. Tentativa de simulação:
        • QA simula transação em ambiente de testes com mesmos parâmetros
        • DevOps replica ambiente de produção em staging para debug isolado
        • Validação: Conseguimos reproduzir o bug? Se sim, qual a causa raiz?
      5. 5. Resolução: Deploy de hotfix, rollback de versão problemática ou restart de serviços
      6. 6. Validação pós-fix: QA testa transações reais em produção (smoke tests)
      7. 7. Post-mortem: Documentação de causa raiz, impacto (quantas transações falharam?), ações preventivas
    • Exemplos de incidentes resolvidos em war room:
      • Caso 1: DynamoDB com ProvisionedThroughputExceededException → Solução: Aumentar WCU (Write Capacity Units) de 50 para 200
      • Caso 2: Cielo retornando timeout após deploy → Causa raiz: Timeout de conexão HTTP reduzido de 30s para 5s por engano → Rollback imediato
      • Caso 3: Transações duplicadas devido a retry sem idempotência → Solução: Implementar chave de idempotência no header X-Idempotency-Key
    • Resultado: MTTR reduzido de 4h para 45min através de processo estruturado e colaboração multidisciplinar

LGPD e Mascaramento de Dados Sensíveis
  • Atuei em validações de conformidade com LGPD (Lei Geral de Proteção de Dados):
    • Mascaramento de dados sensíveis:
      • CPF: XXX.XXX.XXX-## (exibe apenas 2 últimos dígitos)
      • Cartões de crédito: XXXX XXXX XXXX #### (exibe apenas 4 últimos dígitos)
      • Email: f***@***.com (oculta parte do nome e domínio)
      • Telefone: (11) 9****-#### (oculta dígitos centrais)
    • Right to Deletion (Direito ao Esquecimento):
      • Validação de exclusão completa de dados do usuário em todas as bases (user, transactions, cards, addresses, logs)
      • Anonimização de dados em tabelas de auditoria (substituir PII por hash ou UUID)
      • Prazo regulatório: exclusão em até 15 dias após solicitação
      • Certificado de exclusão enviado ao usuário por email
    • Right to Access (Direito de Acesso):
      • Exportação de todos dados pessoais em formato legível (JSON ou PDF)
      • Incluir: dados cadastrais, histórico de transações, cartões vinculados, logs de acesso
      • Prazo: fornecimento em até 15 dias após solicitação
    • Consent Management (Gestão de Consentimento):
      • Opt-in/opt-out de comunicações de marketing (email, SMS, push notifications)
      • Validação de checkboxes obrigatórios vs opcionais em onboarding
      • Registro de timestamp de cada consentimento (para auditoria ANPD)
      • Revogação de consentimento deve ser tão fácil quanto conceder
    • Logs de Auditoria:
      • Rastreamento de quem acessou dados sensíveis (user ID, timestamp, IP, ação realizada)
      • Alertas para acessos anômalos (ex: consulta de 1000+ CPFs em 1 minuto)
      • Retenção de logs por 6 meses (conforme exigência regulatória)

Monitoramento Ativo e Troubleshooting em Produção
  • AWS CloudWatch + DynamoDB para análise de causa raiz:
    • CloudWatch Logs Insights - Queries customizadas:
      • Detecção de padrões anômalos em tempo real
      • Exemplo: fields @timestamp, @message | filter @message like /ERROR/ | stats count() by bin(5m) (conta erros a cada 5 minutos)
      • Dashboards com gráficos de latência P50/P95/P99
      • Rastreamento de request ID único através de toda stack (distributed tracing)
    • DynamoDB - Análise de Transações (Tabela: uat_CREDITCARD_TRANSACTION):
      • Validação direta na base de dados para investigação de causa raiz
      • Campos monitorados: transactionId, transactionStatus, tokenCard, value, retryCount, requestHub, responseHub, updatedDate
      • Estados de transação rastreados: INICIO_PAGAMENTO → EM_CAPTURA → CAPTURADA_FINALIZADA → AUTENTICADA ou ESTORNO
      • Identificação de transações travadas (status não evoluiu após timeout esperado)
      • Análise de retry patterns: retryCount > 3 indica problema sistêmico
      • Correlação transactionId entre DynamoDB ↔ CloudWatch ↔ Response APIs externas
      • Query exemplo: Buscar transação por transactionId: "100-025-2022364-92911-134317215" → Validar se responseHub contém "message": "CAPTURED" e "decision": "ACCEPT"
    • DynamoDB Streams:
      • Rastreamento de alterações em tabelas críticas (users, transactions, wallet, cards)
      • Triggers Lambda para validação de integridade referencial
      • Exemplo: Transação criada mas não finalizada em 10 min → Alarme automático
    • Alarmes configurados:
      • Taxa de erro 500 > 1% → Slack notification + PagerDuty (P2)
      • Latência API > 5s em P95 → Email para Tech Lead
      • Disponibilidade < 99% → Escalar para CTO (P1)
      • Dead Letter Queue > 100 mensagens → Investigação de retry failures
  • War Rooms e Incidentes em Produção:
    • Participação ativa em war rooms para resolução de problemas críticos em produção (incidentes P1/P2)
    • Trabalho conjunto com DevOps:
      • Investigação em tempo real durante incidentes (análise de logs, métricas, traces)

      • Validação de fix com cenário reproduzível antes de deploy em produção

    • Citação e acompanhamento com Devs e PO:

  • Troubleshooting proativo:
    • Identificação de problemas antes de impactar usuários finais
    • Exemplo: Spike de erros 502 detectado às 2h da manhã → Rollback automático acionado
    • Análise de causa raiz documentada em post-mortem (blameless culture)
    • Fluxo de investigação típico:
      1. 1. Alarme dispara (ex: taxa de erro > 1%)
      2. 2. Acesso CloudWatch Logs Insights → Filtrar por ERROR nos últimos 15 minutos
      3. 3. Identificar transactionId afetado
      4. 4. Consultar DynamoDB com esse transactionId → Verificar transactionStatus
      5. 5. Validar responseHub → Identificar se erro veio de parceiro externo (Cielo, Matera, etc.)
      6. 6. Correlacionar com logs de aplicação (stack trace, exception)
      7. 7. Documentar causa raiz + solução + prevenção futura
