QDD: Quality-Driven Development Framework

Quality-Driven Development (QDD) é a evolução do Shift-Left Testing. Não se trata apenas de "testar mais cedo", mas de decidir qualidade antes do código existir: requisitos não-funcionais, critérios de aceite técnicos, estratégias de rollout, métricas de observabilidade e análise de risco.

A Diferença Crítica

No QDD, o QA não é o último a saber. É o primeiro a perguntar. Qualidade orienta as decisões de desenvolvimento, não valida o resultado delas.

QDD vs Shift-Left: A Diferença

Aspecto Shift-Left QDD
O que antecipa Execução de testes Decisões de qualidade
Foco "Testar mais cedo" "Decidir melhor"
Papel do QA Executa testes antes Influencia decisões antes
Momento de ação Quando há código testável Quando há requisito discutível
Artefato gerado Testes automatizados Risk analysis, quality requirements

Framework QDD Operacional (4 Fases)

FASE 1: Discovery & Refinamento

Onde QDD tem mais impacto. QA participa como consultor técnico, fazendo perguntas críticas:

Template de Perguntas Críticas:

  • FINANCEIRO: Qual o impacto financeiro se esta feature falhar?
  • TÉCNICO: Esta operação é idempotente? Como tratamos timeout/retry?
  • OPERACIONAL: Como monitoramos isso em produção? Qual o MTTR aceitável?
  • DADOS: Há PII/dados sensíveis? Como protegemos?
  • CONCORRÊNCIA: Há risco de race condition? Estados inválidos?

Artefato: Quality Requirements Document (QRD)

FEATURE: Pagamento PIX RISCO FINANCEIRO: ALTO (movimentação de dinheiro) REGULATÓRIO: ALTO (BACEN) QUALITY REQUIREMENTS: 1. Idempotência obrigatória 2. Timeout máximo: 30s com fallback 3. Logs estruturados para auditoria BACEN 4. Observability: métricas + alertas 5. Rate limiting: 10 req/seg por usuário CENÁRIOS DE EXCEÇÃO MAPEADOS: - Timeout PSP - Duplicação por retry - Concorrência (múltiplos pagamentos simultâneos) - Reversão/Estorno - Indisponibilidade PSP

FASE 2: Development (QA Embedded)

Daily Touch Points de 15 minutos:

Dia 1: QA questiona decisões de implementação (UUID vs timestamp para idempotency)

Dia 2: QA roda testes unitários no ambiente local, sugere cobertura de cenários faltantes

Dia 3: QA valida logs estruturados e métricas antes do PR

Resultado: Bugs caem de 15 para 2-3, tempo de retrabalho reduz 60%

FASE 3: Testing (Validação)

Pirâmide de Testes Orientada por Risco:

                 /\
                /  \  Manual Exploratory
               /____\  (Exceções, Edge Cases)
              /      \
             /  E2E   \ BDD Scenarios
            /  Tests   \ (Comportamento Negócio)
           /____________\
          /              \
         /   Integration  \ Contract Tests
        /     Tests        \ (APIs, Serviços)
       /__________________\
      /                    \
     /     Unit Tests        \ TDD
    /    (Lógica, Regras)     \ (Cobertura 80%+)
   /__________________________\

Features de alto risco (pagamento): 40% Unit + 30% Integration + 20% E2E + 10% Chaos/Load

Features de baixo risco (layout): 70% Unit + 20% E2E + 10% Manual

FASE 4: Production (Observability)

QDD não termina no deploy. Observability como extensão da qualidade:

# Métricas QDD essenciais # Negócio pagamento_total = Counter('pagamento_total', ['status', 'metodo']) # Qualidade pagamento_latency = Histogram('pagamento_duration_seconds') pagamento_retry = Counter('pagamento_retry_total') timeout_rate = Gauge('pagamento_timeout_rate') # Alertas QDD if timeout_rate.get() > 0.02: # 2% alert_pagerduty("CRITICAL: Timeout PIX > 2%")

Implementação Gradual: Roadmap 90 Dias

Semanas 1-4: Preparação

  • Apresentar conceito para liderança técnica
  • Identificar 1 squad pilot (squad aberto a mudança + produto crítico)
  • Baseline metrics: bugs prod, retrabalho, lead time
  • Workshop QDD (2h) para squad pilot
  • Criar primeiro QRD para próxima feature

Semanas 5-8: Ajustes

  • Retrospectiva QDD: o que está funcionando?
  • Ajustar templates (provavelmente estão muito pesados)
  • Treinar QA em skills técnicos necessários (Docker, API testing)
  • Preparar apresentação de resultados para liderança

Semanas 9-12: Expansão

  • Apresentar resultados (com números!)
  • Expandir para +2 squads
  • Criar "Quality Champions" (1 por squad)
  • Desenvolver biblioteca de Quality Patterns

Critério de Sucesso

-30% bugs em produção + feedback positivo do time em 90 dias

Como Medir Sucesso de QDD

Métricas Leading (Predizem qualidade futura):

  • Quality Requirements Coverage: % de features com QRD completo (Meta: >90%)
  • QA Participation in Refinement: % de refinamentos com QA presente (Meta: 100%)
  • Test Coverage: % de cobertura de código (Meta: >80%)
  • Shift-Left Rate: % de bugs encontrados antes de QA formal (Meta: >60%)

Métricas Lagging (Confirmam qualidade alcançada):

  • Production Defects: Bugs em produção / sprint (Meta: redução de 50% em 6 meses)
  • Mean Time to Detect (MTTD): Tempo médio para detectar bugs (Meta: <2h para críticos)
  • Mean Time to Resolve (MTTR): Tempo médio para resolver bugs (Meta: <4h para críticos)
  • Deployment Frequency: Deploys/semana (Meta: crescimento de 30%)

Métricas de Negócio (Para C-level):

  • Custo de Retrabalho: R$ gastos corrigindo bugs (Meta: redução de 40%)
  • Customer-Reported Issues: Tickets de suporte por bug (Meta: redução de 50%)
  • Revenue Impact: R$ perdidos por indisponibilidade (Meta: redução de 60%)
  • Time to Market: Dias de ideia a produção (Meta: redução de 25%)

Desafios Reais e Como Superá-los

1. "Não temos tempo para isso"

Resposta com dados: "Semana passada vocês gastaram 32 horas corrigindo bugs que poderiam ter sido evitados. QDD teria custado 3 horas de refinamento. ROI: 10x"

Estratégia: Começar com features críticas (alto risco), versão "light" de QRD para features simples, mostrar resultados rápidos (4 semanas).

2. "QA não tem senioridade técnica"

Solução:

  • Upskilling gradual: Curso interno de Docker, APIs, Git / Pair testing com dev
  • Shadowing: QA júnior acompanha QA senior em refinamentos
  • Especialização: QA de pagamentos especialista em idempotência, QA de integrações em APIs

3. "Cultura de blame"

Solução:

  • Reframe: QA não questiona dev, questiona o SISTEMA
  • Linguagem: ❌ "Você pensou em timeout?" → ✅ "Precisamos definir estratégia de timeout"
  • Blameless RCA: Focar em processo, não pessoa
  • Celebração conjunta: Quando QDD evita bug, celebrar time TODO

4. "Gestão cobra velocidade, não qualidade"

Solução:

  • Educar com números: Mostrar que qualidade AUMENTA velocidade (menos retrabalho)
  • Mudar métricas: Adicionar "bugs em produção" ao dashboard de gestão
  • Correlacionar: Qualidade com NPS/satisfação cliente

Conclusão

QDD não é mágica. É disciplina.

É o compromisso de que qualidade não é responsabilidade do QA. É responsabilidade do TIME. E o QA é quem guia esse compromisso.
